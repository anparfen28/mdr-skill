# Крайние случаи и разрешение противоречий (читать при неоднозначном лиде)

Сюда собраны правила для нестандартных лидов и коллизий, чтобы вердикт был однозначным на любом ивенте. Составлено по аудиту скилла 18.07. Если основной поток (SKILL.md шаги) даёт неоднозначность — правило здесь.

## Разрешение коллизий порогов и пайплайнов
- **Won-и-ушёл (была won-сделка, потом клиент отвалился):** ⚠️ коллизия порогов 6 мес vs 3 мес **снята с 20.07** — правило одно для всех статусов: **занят (двустороннее общение <3 мес ИЛИ договорённость на ближайшие 3 мес) → не пишем**. Дату терминального события (lost/won) с порогом больше не сравниваем, она идёт в «Сделка на компании» как контекст.
- **Won с реальной продажей (value > 0 ИЛИ стадия «Оплата»/рабочий sales-пайплайн 53):** это **платящий клиент**, а НЕ «успех MDR-воронки» → трактуем как **Действующий (не пишем), независимо от поля «Статус клиента», возраста сделки и даты касания**. Это правило тест занятости НЕ отменяет — оно строже и живёт отдельно: won с value 0 в pipe 7/49 = не клиент (доход доходит лишь до встречи, не до оплаты), решает занятость контакта; won с деньгами = клиент, молчим всегда.
- **Pipe 7 — и рабочий, и шумовой:** все новые лиды падают в pipe 7 (этап «Входящие» 44). ⚠️ С 20.07 шаги и задачи ПО СДЕЛКЕ вообще не участвуют в вердикте: открытая сделка в любом пайплайне не блокирует — блокирует занятость КОНТАКТА (см. `pipedrive_fields.md`). Различение pipe 7 нужно только для батчей: автосайнап (pipe 46 всегда + pipe 7 на самом старте, стадия «Входящие»/«Отквалифицирован») сделкой не считаем → лид идёт в батч 3 «Новый» и квалифицируется полностью; продвинутая сделка в pipe 7 → батч 2.
- **Сделка на орг, но не на нашей персоне:** пишем персоне, если она свободна (правило 20.07). Сделка на другом человеке не блокирует и вдобавок НЕ даёт нашей персоне «должность целевая по умолчанию» — её должность проверяем обычным порядком. Привязан к сделке → должность не пересуживаем. См. `pipedrive_fields.md`.

## Компания — нестандартное
- **Дубли организации** (один домен = 2+ org_id): перед вердиктом матчить org по **нормализованному домену**; при двух записях **склеить статус, беря худший для работы** (Действующий / в-воронке / won перебивают «Новый»), иначе ложное «Новый» + дубль-строка.
- 🚨 **ПУСТАЯ ОРГ-КАРТОЧКА У ОЧЕВИДНО КРУПНОЙ КОМПАНИИ = КРАСНЫЙ ФЛАГ, А НЕ «НОВЫЙ ЛИД».** Самая дорогая ошибка прогона 18.07 (**4 случая из 28**). Механика бага: регистрация с лендинга/попапа создаёт **новую пустую орг** под вариантом домена, персона цепляется к ней, и квалификация видит «нет сделок, нет статуса → Новый, Работаем = Да». Дедуп по домену это **НЕ ловит**, потому что строки доменов разные:
  - **T2:** персона на пустой `t2.ru` (834559), реальная карточка `tele2.ru` (332888) — **действующий клиент** (won 250k 12.2023, открытая сделка MobilePush). Часть 1 показала «Сделка: Нет · Новый · Работаем: Да» → заход ушёл бы действующему клиенту в обход владельца сделки.
  - **Центральный университет:** 5 дублей орга, свежие регистрации падают на пустую `cu.ru`; на реальной карточке — отказ 15.06.2026 «идею внедрять CDP на текущем месте я похоронила».
  - **PlanetEnglish:** орг 236311 (размеченная, история с 2019) vs 852490 (создана попапом 15.07).
  - **Hoff:** вся история на персоне 274919, свежая регистрация — на 736379.
  - **Детекция (обязательна для каждого лида уровня Silver+ и любой узнаваемой компании):** орг-карточка пустая (нет индустрии/уровня/статуса/сделок), НО компания явно живая и крупная (трафик, известный бренд, Enterprise-домен) → **искать дубль по НАЗВАНИЮ** (`searchOrganization(term=<название бренда>)`), а не только по домену; проверить варианты домена (`t2.ru`/`tele2.ru`, `cu.ru`/`centraluniversity.ru`, бренд.ru/бренд.com). Нашёл дубль → **брать худший для работы статус** и вести лида по РЕАЛЬНОЙ карточке.
  - ⚠️ Тот же класс бага в обратную сторону: **lost-сделка с причиной «MDR: тест или дубль»** (Hoff, 04.2026) — это техническая чистка, а НЕ отказ клиента. Не считать её терминальным событием и не ставить из-за неё «Отток». Читать `lost_reason`, а не только факт lost.
- **JS-SPA / сайт, который WebFetch видит пустым, но бизнес реальный** (Vue/React, отдаёт только лоадер — как каталог партнёров Mindbox): пустой/скелетный ответ WebFetch на СУЩЕСТВУЮЩЕМ домене ≠ мусор. **Добить браузером.** Ставить «Нецелевая (не бизнес)» — только если и браузер показывает отсутствие бизнеса. (Тот же класс бага, что SVG-трафик.)
- **Припаркованный / «продаётся» домен** (Sedo, domainregistryinc, generic-заглушка) → Нецелевая, «припаркованный домен». Но реальный работодатель персоны может быть другим (см. ниже).
- **Компания без сайта** (только приложение / продавец на маркетплейсе / соцсети) → квалифицировать по приложению/витрине/соцсети, НЕ Нецелевая по «нет сайта».
- **Нет org и нет домена вообще** → 🟡 Уточнить (компания неизвестна), не Нецелевая по умолчанию.

## Персона — нестандартное
- **Сменила работодателя** (пример: Минас Саакян — в CRM на Яндекс.Маркете, а по свежим регистрациям с `@tbank.ru` уже в Т-Банке): CRM-привязка org **устарела**. Детекция: **домен email персоны ≠ домен привязанной org** (личные почты gmail/mail не в счёт) ИЛИ свежая заметка о смене места. → пометить «привязка устарела, org уточнить», квалифицировать/писать под НОВОГО работодателя или employer-agnostic по отношениям, НЕ «win-back старой компании».
- **Несколько org у одной персоны** (конфликт привязки — LEON vs nabu.com): квалифицируем/пишем ту org, что совпадает с **ивент-контекстом / доменом рабочей почты**; вторую (мусорную/старую) игнорируем.
- **Пустая роль И пустой тир, ничего не нашли** (сайт/LinkedIn) → дефолт **🟡 Уточнить (роль неизвестна)**, компанию не терять (аналогия с Wood-дефолтом уровня).
- **>1 целевой регистрант из одной компании** (Часть 2, дедуп): оставляем самого **ЛПР-ного** (тир «Менеджмент» > «Линейный»); при равенстве — с более маркетинговой ролью (CRM/CMO/лояльность).

## Индустрия/гео — нестандартное
- **Гео СНГ шире, чем РФ/КЗ/РБ:** работаем с **РФ, Казахстаном, Арменией, Беларусью**. Прочие СНГ (Узбекистан, Кыргызстан, Азербайджан, Грузия) — оцениваем по локальным рейтингам, передаём в Midmarket/Enterprise, не автостоп. Украина — нет. ЕС/США — отдельная команда (не РФ-команда), не квалифицируем как своё.
- **НКО / Благотворительность** — статус ЦА в Notion не финализирован («под вопросом») → **🟡 Уточнить**, не автостоп и не авто-🟢.
- **Инфобизнес** → 🟡 Уточнить (работаем только при невозвратном авансе на 3 мес — выяснить на звонке).

## Часть 2 (заходы) — нестандартное
- **Свежий отказ / «встреча была, сказали нет» / «не интересно»** (не lost-сделка, а разговор): это **двустороннее** общение (клиент ответил, пусть и отказом) → попадает под общий порог **3 мес** от даты этой активности. < 3 мес → «Работаем» = Нет, причина «свежий отказ, выждать»; ≥ 3 мес → можно заходить заново, но в брифе обязательно указать прошлый отказ и его причину (заход не должен выглядеть первым холодным касанием). ⚠️ Если отказ сопровождался договорённостью («вернуться в новом бюджетном цикле») — блокирует до её срока, даже когда 3 мес прошли.
- **Лид ведёт партнёр** (поле «лидогенератор» / в заметках «ведёт {агентство}»): прямой заход MDR может конфликтовать → пометить в брифе «синхронизировать с партнёром до пуша», CTA мягче.
- **Нет числового кейса под нишу** в `case_library.md`: фолбэк — стиль Андрея (2–3 наблюдения по сайту БЕЗ кейса) ИЛИ назвать крупного клиента без цифр «для доверия». Не выдумывать цифру.
- **Нет email у персоны** → колонку «Заход — Email» оставить пустой/«нет email», готовить только Telegram.

## Домены/техника
- **Кириллический / IDN-домен** (`домен.рф`): при фетче/навигации — punycode (`xn--…`); в ячейку «Основной сайт» писать как есть, строчными.
