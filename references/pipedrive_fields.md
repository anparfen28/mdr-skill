Окно, упёршееся в лимит вызовов, ОБЯЗАНО вернуть `incomplete` с непокрытым интервалом — молчаливый недобор запрещён (разведка 19.07 именно так дала 565 как «нижнюю границу», покрыв лишь 11–18 июня).

**Анкета в `note`** (HTML, разделитель `<br>`, строки «Ключ: значение»): `eventId`, `eventName`, `siteUrl`, `Имя`, `Email` (внутри `<a href="mailto:">`), `Должность`, `Телефон`, **`Размер базы`**. ## Открытая сделка орга → «Открыта · <Стадия> · owner <Имя> · <N> касаний»
> ⚠️⚠️ **ПЕРЕПИСАНО 21.07.2026. Поштучный рецепт «3 вызова на орг» ОТМЕНЁН.**
> Старая версия велела `getDeals(org_id=…)` в цикле по организациям и точечный `getStage(id)` — это и сожгло прогон 17.07 (**1498 вызовов, 71% токенов**). `workflow.js` теперь прямо ЗАПРЕЩАЕТ такой цикл. Если читаешь этот раздел как инструкцию — читай новую.

**Как собирать правильно (пачками, ~15 вызовов на весь ивент):**
1. **Стадии — ОДИН вызов:** `getStages(limit:500)` → словарь `stage_id → {name, pipeline_id, order_nr}`. ⚠️ Именно так, а НЕ точечный `getStage` на каждую сделку.
2. **Открытые сделки — пачками по пайплайнам** (`pipelines.working`, обычно 7/49/53):
   `getDeals(pipeline_id:<p>, status:"open", limit:500, custom_fields:"<deal.compact_probe>", include_fields:"activities_count")` + курсор.
   ⚠️ `custom_fields` обязателен — иначе блоб из 60+ полей раздувает ответ до ~4KB/сделку. `include_fields` — скаляр, не CSV.
   Шумовые пайплайны (`pipelines.noise`, 46 «Регистрация на видео-курс») НЕ запрашиваем вовсе.
3. **Связка локально:** оставить сделки, чей `org_id` есть в списке кандидатов.
4. **Имена владельцев** — только для отобранных: уникальные `owner_id` → `getNotes(user_id:<id>, limit:1)` → `data[0].user.name`, кэшировать. Имена НЕ выдумывать.

**Что вернуть по каждой орг:** `in_funnel` · `cell` («Открыта · <стадия> · owner <Имя> · <N> касаний») · **`person_ids`** (кто привязан к сделке — от этого зависит, проверять ли должность) · `won_month` · **`paying`** (won с `value>0` / pipe 53 / стадия «Оплата» = платящий клиент).

⚠️⚠️ **АВТОСАЙНАП В PIPE 7 — НЕ СДЕЛКА.** В pipe 7 падают ВСЕ новые лиды с формы «Демо». Открытая сделка в pipe 7 на стартовой стадии («Входящие», «Отквалифицирован») = сырой инбаунд → `in_funnel=false`, лид идёт в батч 3. Продвинулась дальше («Начали общение», «Целевой контакт найден» и позже) → настоящая воронка. Не отсечёшь — любой, кто когда-то оставил заявку, получит «компания и должность целевые по умолчанию» без проверки.

**Выбор сделки, если открытых несколько:** отсечь шум (pipe 46; pipe 7 на старте), из оставшихся брать самую продвинутую по `order_nr` либо по `value` desc. Реальных >1 → показать выбранную + «+N ещё открытых». Открытых 0 → «Не в воронке» (не полагаться на счётчики `getOrganization` — там смешаны won/lost).

Касания = `activities_count` (done+undone). Только состоявшиеся — `getDeal(id, include_fields="done_activities_count")`. ⚠️ Это для КОЛОНКИ таблицы, а не для вердикта: шаги по сделке на «пишем/не пишем» не влияют (решает занятость контакта).

### ⚠️⚠️ Открытая сделка САМА ПО СЕБЕ не блокирует — блокирует занятость КОНТАКТА (модель уточнена 20.07.2026)
Раньше любая открытая сделка на орг = «В воронке» = не пишем. Теперь сделка на компании вообще не является критерием: **решает только тест на занятость по нашему человеку** (см. следующий раздел).
- Наличие открытой сделки говорит одно: **компания целевая** (сделки заводят только с целевыми) → её не нужно квалифицировать заново.
- Кому писать внутри этой компании — решает занятость конкретного контакта, а не факт сделки и не её стадия.
- Сделка идёт с ДРУГИМ человеком компании, а наш в ней не участвует → нашему **пишем**. В «Сделка на компании» пометить «Открыта на компании (другая персона: <Имя>) · пишем».
- ⚠️ Закрепление консультанта **за компанией** или **за карточкой контакта** человека НЕ занимает. Занимает только реальная работа по нему: свежее касание или запланированная задача.
- ⚠️ Что осталось в силе: сделку смотрим **на той же организации**, а не по `open_deals_count` персоны — у персоны бывает висящая сделка на ЧУЖОЙ орг (nabu.com у персоны со сделкой по leon.ru).
- Стадия, owner и число касаний по сделке нужны **для колонки таблицы** (MDR читает контекст), а не для вердикта.
## ⚠️⚠️ ГЛАВНЫЙ ТЕСТ: занят ли КОНТАКТ (модель уточнена 20.07.2026)

**Заменяет прежнее правило «won ≤ 6 мес» (правило Анны 17.07) и правило «открытая сделка на орг = не пишем».** Ни исход сделки, ни её наличие, ни закреплённый консультант больше не решают — решает работа по конкретному человеку. Порог везде **3 месяца**.

🔑 **Блокирует не факт активности, а ДВУСТОРОННЯЯ ДОГОВОРЁННОСТЬ с клиентом о контакте.** Односторонняя работа консультанта человека не занимает.

**Контакт ЗАНЯТ (не пишем), если выполнено хотя бы одно:**
1. **Двустороннее общение < 3 мес** назад — клиент **отвечал**, участвовал в разговоре.
2. **Есть договорённость о контакте в ближайшие 3 месяца** — согласованный с клиентом следующий шаг («бюджета нет, обсудить условия в конце квартала в цикл бюджетирования», «созвониться после отпуска»). ⚠️ Блокирует **независимо от даты общения**: разговор мог быть полгода назад, но если из него следует контакт на следующей неделе — человека ведут, не перехватываем.

**Контакт СВОБОДЕН (пишем), если:** двустороннего общения не было или оно ≥ 3 мес назад, **И** договорённостей на ближайшие 3 месяца нет.

**⚠️ НЕ блокируют, даже если активность свежая:**
- **общение «в одни ворота»** — консультант писал/звонил, клиент не ответил. Это не отношения, а попытка;
- **односторонняя задача** «попробовать зайти», «прозвонить», «написать ещё раз» — клиент о ней не знает и ничего не обещал.

**Окно договорённости = окно общения (3 мес).** Договорённость **дальше** 3 месяцев не блокирует — «вернуться через год» не должно закрывать контакт навсегда. ⚠️ **Просроченная** незакрытая задача (дата в прошлом) — по текущему допущению **не блокирует**, но помечается в причине: обычно это «собирались, но не дошли», а не активная работа. Допущение спорное, вынесено на подтверждение.

⚠️ **Это суждение по СОДЕРЖАНИЮ, а не по типам и датам.** Двусторонность и наличие договорённости вычитываются из `note` активностей, саммари звонков (tl;dv) и текста задачи. Тип активности и её дата этого не показывают. Сомнение и следа ответа клиента в содержании нет → **договорённостью не считаем**, лид уходит в работу.

**Привязка к сделке отменяет проверку должности.** Если лид привязан к открытой сделке — его должность целевая по умолчанию: раз привязали, релевантным уже признали (в сделке вполне может сидеть «Директор по IT», ведущий внедрение). Не привязан — должность проверяем обычным порядком. Поэтому фаза Deals обязана возвращать **`person_ids`** — id всех людей, привязанных к открытым сделкам орга.

- **Исход сделки не важен:** won / lost / открытая — отдельного won-порога нет. Won отображается в «Сделка на компании» как контекст («Выиграна {YYYY-MM}»), но вердикт не определяет.
- **Закрепление за компанией не занимает человека.** Консультант может стоять в карточке орга или контакта — если по контакту 3 месяца нет двустороннего общения и договорённостей нет, забираем.
- Орг «Действующий» (поле `c02f2a2f…`) → **не пишем в любом случае** (это уже клиент — не менялось).

**Считаем по ПЕРСОНЕ, не по организации.** Свежее общение с её коллегой нашего человека не закрывает: разные люди — разные разговоры.

⚠️⚠️ **РЕГИСТРАЦИЯ НА ИВЕНТ — НЕ ОБЩЕНИЕ. Главная ловушка этого правила.**
Регистрация лежит в Pipedrive как активность (`type = registratsiya_na_sobitie`), поэтому у **каждого** регистранта `person.last_activity_date` = дата ивента, то есть «общение сегодня». Взять `last_activity_date` в лоб → весь список окажется «свежим» и мы не напишем НИКОМУ. Считать общением только **человеческое двустороннее** взаимодействие.

**Рецепт проверки (на персону) — ОДИН вызов даёт все сигналы:**
```
getActivities(person_id:<id>, limit:50, sort_by:"add_time", sort_direction:"desc")
```
1. Выбросить `type == "registratsiya_na_sobitie"` (регистрации на ивенты и курсы — автоматика, не общение).
2. **ЧИТАТЬ СОДЕРЖИМОЕ** оставшихся: `note`, саммари звонков (tl;dv), текст задачи. Без содержания двусторонность и договорённость не определить — тип и дата их не показывают.
3. **`last_touch`** — «YYYY-MM» последнего **ДВУСТОРОННЕГО** общения (`done == true` И виден ответ/участие клиента: состоявшийся звонок, встреча, ответное письмо). Клиент ни разу не отвечал → `""`.
4. **`one_way_touch`** — «YYYY-MM» последнего касания **в одни ворота** (писали, ответа нет). Только для лога, НЕ блокирует.
5. **`planned_task`** — «YYYY-MM-DD» ближайшей незакрытой (`done == false`) задачи + владелец. Дату брать КАК ЕСТЬ (просроченные и далёкие тоже) — в окно 3 мес её укладывает скрипт.
6. **`task_agreed`** — главное суждение: `true`, только если задача отражает **договорённость с клиентом**; `false`, если это одностороннее напоминание себе («попробовать зайти»). Сомнение → `false`.
7. **`evidence`** — строка-обоснование (цитата/факт), по ней MDR проверит решение.
8. Текущую дату брать `date +%F`, не выдумывать.

⚠️ Все сигналы приходят из ОДНОГО вызова — не делать второй проход по персоне.
⚠️ Пороги считает `scripts/apply_touches.py`, агент их НЕ применяет: его работа — прочитать смысл и честно разметить.

⚠️ **Когда проверять — на шорт-листе, а не по всей базе.** Один `getActivities` на персону × 1000 регистрантов = повтор токенового провала 17.07. Проверять только тех, кто прошёл все дешёвые фильтры и иначе получил бы «Работаем = Да / Уточнить» (обычно десятки строк). Остальным занятость не считаем — им и так не пишем.

Пример пересчёта на 260722: по старому правилу 6 из 14 won-орг были заблокированы как «свежий won» (pn.ru, agr.auto, kataacademy, moysklad, biocad, luchi). По новому правилу won-дата их больше не блокирует — блокирует только реальное касание персоны моложе 3 мес, так что часть из них открывается. ⚠️ Цифры прежнего прогона пересчитаны НЕ были — при первом прогоне по новому правилу сверить руками.

## Гочи
- Нет эндпоинта метаданных полей → числовые (выручка/база/трафик) неоднозначны, брать из заметок.
- Контекст на **ORG + PERSON, не на сделке**. Всегда подтягивать связанные org и person.
